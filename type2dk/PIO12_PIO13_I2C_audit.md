# Type2DK PIO12・PIO13のI2C調査（2026-09-16）

## 2026-09-17追記：100 kHz受信と電源実測

CoreS3 1.1.0＋2DK v5のユーザー提供ログでは、attempts=2076→3076に対しok=1510→2510で、区間内の1000回すべて正常。nack=566は増えず、timeout/other/bad/gapsはいずれも0でした。DIAGはread=VALID。probe=NO_ACKは以前の単発PROBEの結果が残ったもので、現在の受信失敗を意味しません。100000は設定クロックであり、オシロスコープによる実測ではありません。400 kHzは未確認です。

ユーザーは外付けプルアップの電源配線を押さえると改善したと報告しており、接触不良が有力候補です。またTP18（VDD_3V3_MCU）を3.0 Vと実測しました。CoreS3 v1.1.1はPORT Aの内蔵プルアップを無効化し、SDA/SCLそれぞれの2 kΩをTP18へ接続する手順に更新します。CoreS3の3V3との直接接続はしません。v1.1.1と配線変更後の実機確認は別途必要です。2DK v5のBINは維持します。以下は各時点での調査記録です。

## 判定と、試験版の誤り

QN9090のPIO12・PIO13にはハードウェアI2C1のSCL・SDAが割り当てられ、スレーブに使用できる。400 kHzはFast-modeの対応範囲。Type2DKモジュールにも両信号が出ている。

ただし、**本リポジトリのv1〜v3はピン機能番号をFUNC4と誤って指定していた。FUNC4はPWMであり、I2C1はFUNC5。v4で修正した。** チップが対応することと、配布したプログラムが正しく設定されていたことは別だった。

## v4の実機ログで追加確認できたこと

最新ログではSTATEのbeatが増え、UART動作を確認できた。PIO12/13は両方0x595、CFG=2、SLVADR0=0x84、clock_gate=0x4800のI2C1 bit14=1、reset=0x10000000のI2C1 bit14=0。PSELIDは0であり、これだけがv4のready条件と一致しない。STAT=0x801はSLVPENDING=0、SLVNOTSTR=1。スレーブの処理待ちやクロックストレッチを示す値ではない。

v4はready=0でもスレーブとNVICを有効化済み。PSELIDの判定不一致をNO_ACKの根本原因とは断定できない。SDKのQN9090.hではI2C_Typeの0xFF8は予約領域（0xFFCはID）だが、汎用FLEXCOMMドライバはPSELIDへアクセスする。この不整合があるため、実機のPSELID=0だけで機能非対応とは結論しない。

v5は同じI2C設定を維持し、GPIO入力での3秒観測、FUNC5に戻した後の入力観測、CHECKの個別判定、ID/INTEN/INTSTAT/クロック選択/CPU割り込みマスクを追加する。通信成功を確認した修正版ではない。[v5の試験手順](README.md)。以下の過去の調査記録にある「UART未確認」は、この実機ログで更新される。

## 必要なファームウェア設定

v4では次の設定を使用する。信号線へ出力されるSCLの周波数はCoreS3（マスター）が決める。

| 設定 | v4 |
|---|---|
| PIO12/13のピン機能 | IOCON FUNC=5、デジタル有効、内部抵抗なし、疑似オープンドレイン有効 |
| IOCON設定値 | 両方とも0x00000595 |
| 周辺回路選択 | I2C1をスレーブ有効化。FLEXCOMM3 PSELIDへ3を書いたが実機の読み戻しは0。意味は上記のとおり未確定 |
| アドレス | 7ビット0x42、SLVADR0=0x84 |
| 機能クロック | FRO32M由来の32 MHz |
| CLKDIV | 8。スレーブのデータ設定時間を確保する値で、SCLを32 MHz/9で駆動する意味ではない |
| 応答 | アドレス・送信要求・選択解除の割り込みを処理 |
| 省電力 | このI2C単体試験では使用しない |

ユーザー提供SDKの `fsl_i2c.c` の `I2C_SlaveDivVal` / `I2C_SlaveInit` と照合した。32 MHz・Standard-modeではCLKDIV=8になり、SDKのコメントも速度未確定時は長い設定時間のStandard-mode設定を使うとしている。従ってCLKDIV=8自体は「400 kHzに対応しない」という意味ではない。ハードウェアは必要に応じてクロックストレッチする。

SWDとI2Cは同じ2ピンの機能選択なので、I2Cに切り替えた状態で同じピンをSWDとして同時使用できない。既存SWDプローブは外す。USB書き込み・ログに使うPIO8/PIO9のUART経路は別である。

## 電気的条件と400 kHzの確認

PIO12/13は通常I/OセルによるI2Cで、PIO10/11の専用I2Cセルとは区別する。1 MHzや3.4 MHzの対応をそのままPIO12/13へ適用しない。

3.3 VのI/O電源で使う場合は、SDA・SCLをそれぞれ3.3 Vへ外付けプルアップし、GNDを共通にする。PORT Aの赤5 Vへはプルアップしない。短い配線では各2.2 kΩを試験開始値にできるが、最終値は電源・並列抵抗・バス容量と波形で確認する。NXP Table 17にはPIO12/13を含むLS端子の2 mA負荷条件がある。3.3 V/2.2 kΩは最大約1.5 mA（他の抵抗が並列にない場合）。

SDK・レジスタ・ビルドの確認だけで、400 kHzの波形、割り込み応答、UWB/BLEとの同時運用を検証したことにはならない。今回のv4はUWB/BLEを動かさない単体試験。後でUWBと統合する際は省電力も見直す。NXP Table 8（p.30）はI2C1のPower-downからの直接wake-upを対応ありとはしていない。

## 現在のログについて

ユーザーのCoreS3ログは100 kHz、受信成功0回、未通信時にもidle=0/0。2DK USBログは無出力との報告。旧版でPWMを選んでいたことは確定したソフトウェア不具合であり、I2Cが端子へ出ない原因になる。ただし両線Lowの物理原因やUSB無出力の原因を、この誤設定だけで確定することはできない。

旧版のready=1は、誤った設定値を書いて同じ値を読み戻した場合にも成立するため、機能番号の誤りを検出できなかった。v4には実際のピン設定ヘルパーを公式表のFUNC5と照合するホスト回帰テストを追加した。FUNC4へ戻した場合にテストが失敗することも確認する。

## v4で確認する順番

1. 機器間の配線を外し、2DK単体へv4を書き込んでFlash照合を確認。
2. 2DK USBを115200 bps / 8N1 / フロー制御なしで開き、STATE,v=4を確認。
3. REGのpio12/13が0x00000595であることを確認。
4. 電源を切ってSDA/SCL/GNDとプルアップを接続し、100 kHzのPROBE/READを試す。
5. 100 kHzで応答を得てから400 kHzを試す。

**この節の手順作成後、v4の実機起動・UARTは確認済み。I2C通信は未確認。最新手順はv5のREADMEを参照。**

公開資料・公開コードを追加検索した範囲では、「Type2DK EVK Rev.4.1のPIO12/13を400 kHzのスレーブとして動かした実測例」は見つからなかった。これは不可能という証拠ではないが、本試験を実機検証済みとは扱えない。

QN9090の詳細ユーザーマニュアルUM11141は[NXP製品ページ](https://www.nxp.com/products/QN9090-30)でアカウント必須と表示され、今回本文を取得できていない。公開データシート、公開アプリケーションノート、ユーザー提供SDKのヘッダとドライバを使用した。UM11141全文を読んだとの主張はしない。

### プルアップの位置と電気的な余裕

共有された `Type 2DK UWB Bluetooth LE Combo Module Datasheet-J.pdf` の冊子p.27、Figure 13では、外付けプルアップはPIO10/SCLとPIO11/SDAに描かれている。PIO12/SWCLKとPIO13/SWDIOには描かれていない。これはモジュールの参考回路であり、Rev.4.1 EVKの実装抵抗を証明する図ではない。

PIO12/13の内部プルアップが存在することと、400 kHzで十分な立ち上がりが得られることも別である。NXPデータシートTable 17の内部抵抗は40〜60 kΩ。短い配線でも、外付け抵抗なしで400 kHzを保証できない。

[NXP I2C-bus specification UM10204 Rev.7.0](https://www.nxp.com/docs/en/user-guide/UM10204.pdf)のTable 11と7.1節を使うと、Fast-modeの立ち上がり上限は300 ns、単純な抵抗プルアップの概算は `tr = 0.8473 × Rp × Cb`（30〜70%間）となる。

| プルアップ | 仮定した総バス容量 | 計算した立ち上がり時間 | 300 nsとの比較 |
|---|---:|---:|---|
| 2.2 kΩ | 50 pF | 約93 ns | 下回る |
| 2.2 kΩ | 100 pF | 約186 ns | 下回る |
| 2.2 kΩ | 200 pF | 約373 ns | 超える |
| 50 kΩ（内部抵抗の代表値） | 50 pF | 約2,118 ns | 超える |

容量は計算例であり、ユーザーの配線を測定した値ではない。2.2 kΩなら配線に関係なく400 kHzが保証される、という意味ではない。低レベル電圧、並列抵抗、立ち下がりも確認する。

### 400 kHzとソフトウェア負荷

400 kHzのクロックはCoreS3が生成し、2DKはI2C1のハードウェアでビットを処理する。1ビットごとにソフトウェアでGPIOを操作する方式ではない。SDKの `I2C_SlaveInit` と `I2C_SlaveDivVal` はクロックストレッチ時の設定時間を扱う。実際の読み取り時間には、ストレッチとソフトウェアの待ち時間が加わる。

7ビットアドレスの単純な16バイト読み取りなら、アドレスを含む17バイト×9クロック = 153クロック。400 kHzでは約382.5 µsがクロック部分の理論値になる。仮に毎秒50回ならこの部分の占有率は約1.9%。START/STOP、ストレッチ、再試行は含まない。距離情報の更新が400 Hz未満でも、この計算から通信容量の見通しは立てられるが、実機性能の保証ではない。

### 省電力とSDKへの統合

NXPデータシートTable 8では、I2C1のDeep-sleepからの復帰は対応、Power-downからの復帰は対応とされていない。I2C0とは異なる。[NXPサポートのQN9030に対する説明](https://community.nxp.com/t5/Other-NXP-Products/I2C-resistors-pull-up-not-high-while-Power-Down-mode/td-p/1547851)も、Power-down復帰をI2C0に限定している。QN9090への判断根拠は同チップを明記したデータシートとする。

v4は省電力へ移行しない。UWB/BLEアプリへ統合する際にはPower-down設定と復帰後のピン・クロック再設定を改めて調べる。SDKに `BOARD_InitSWDPins()` が存在するため、他の処理が同じPIO12/13をSWDへ戻さないことも確認対象となる。ただし、現在のv4がこの関数を呼ぶという意味ではない。

### UART無出力についての訂正と切り分け

v3で非同期APBブリッジ設定を追加したことはSDKとの差分を埋める変更であり、UART無出力の原因がその設定不足だったと確認できたわけではない。NXP Errata SE302はUSART/SPI/ADCへのアクセスをAHB port 7に関連付けている。「USART0が非同期APB上なので、この設定だけで直る」という説明は根拠不足である。

v4のBOOTログは、PIO12/13をI2Cへ変更する約2秒前に送信する。従って、CoreS3とSWDプローブを外し、2DK単体でもBOOT・STATEが一切出ない場合、FUNC5の選択だけを追加変更しても問題は切り分けられない。書き込み照合、ISP解除後の起動、115200 bps/8N1/フロー制御なし、UART経路、独自起動処理のいずれかが未確認である。

CoreS3の `idle=0/0` は、GPIO2/1をデジタル入力で読んだ結果であり、オシロスコープで両線0 Vを確認したという意味ではない。`before=0/0` が最初のPROBEより前に出るため、「2DKが読み取り要求を受けてストレッチしている」ともまだ判断できない。

次の実機確認は、(1) 2DK単体で起動ログ、(2) SDA/SCLの待機High、(3) 100 kHzで0x42へのACKと有効なデータ、(4) 400 kHzで同じデータと波形、の順になる。100 kHzでも未通信時からLowという現在の結果は、400 kHzの処理能力を測定した結果ではない。


## Rev.4.1評価基板回路図の追加確認

ユーザー提供 `MTD_SCH_011-E-2DK-EVK-Rev4.1_Schematic.pdf` を全4ページ確認した。4ページの改訂履歴は2024.2.14 Rev.4.1。変更内容はR1/R2をSE051WブロックからType2DKモジュール側へ移動。元PDFは公開リポジトリへアップロードしない。

- 1ページ：QN9090 SWDコネクタTP8の2番=SDA候補PIO13、4番=SCL候補PIO12。3/5/9番=GND、1番=VDD_3V3_EVB。7/8番は図上未接続。
- PIO12/13とTP8の間は直接接続。別IC・バッファ・直列抵抗・外付けプルアップは図示されていない。FUNC5でI2C1へ転用することを妨げる基板上の回路は、この回路図からは見つからない。
- R1/R2はPIO10/11からVCC_SEへの10 kΩ抵抗でDNI。PIO12/13とは別ネットで、今回のプルアップを代用しない。
- 3ページ：MCU電源はTP18=VDD_3V3_MCU、GNDはTP15。TP11=VDD_3V3とTP18の間のR21は0 Ω・DNIで、実物のジャンパ等の導通状態を確認する。TP8の1番は別分岐のEVB電源で、そこに電圧があってもMCU電源を証明できない。
- USB側LDOの3.3 V出力はD1を通り、SW2の選択後にVDD_3V3へ至る。電圧降下があるため、MCU電圧を一律3.3 Vと断定しない。プルアップは測定したMCU I/O電源に合わせる。
- FT230XのVCCはVCC_USBへ接続されるため、MCU給電が成立しなくてもUSB側だけ認識される状態は回路上あり得る。現在のUART無出力の原因が電源だと確定したわけではない。
- QN9090のUSB UARTはPIO8/PIO9。TP1/TP2はSR040 UART、TP4/TP5はFT230X CBUS0/1で、QN9090 UARTの取り出し点ではない。
- CBUS2はR4を介してQN9090 RESET、CBUS3はR8を介してPIO5へ接続。USBの書き込み制御はPIO12/13とは別経路。回路図だけではFT230X内部設定や現在の制御信号レベルまでは確認できない。

ピン番号は回路図の番号であり、実物の左右・上下はコネクタの1番表示で確認する。物理的な配置図と回路図のシンボル配置は同一ではない。[更新した接続・電源確認手順](README.md#rev41回路図で確認した接続)。
